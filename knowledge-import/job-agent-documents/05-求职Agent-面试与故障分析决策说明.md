## 为什么使用 Agent/图编排，而不是只有固定 Workflow
- 简历改进不是纯线性流程：质量检查后需要**条件路由**（超页打回 needs_revision，通过进 await_review），且每个节点（JD 分析器、检索器、模型客户端、检查器）都是可独立替换/注入测试替身的服务——LangGraph StateGraph 提供了状态共享 + 显式路由 + 节点可替换三件事〔代码确认：resume_graph.py 构造参数注入〕
- 但项目刻意**不拆多子 Agent**：一个垂直流程图足够，避免为演示而过度设计〔文档确认：README + docs/第一版范围.md〕

## 哪些步骤适合确定性 Workflow（不调模型）
- JD 分类与关键词提取（jd_analyzer 规则）
- 检索与排序（knowledge_retriever）
- 质量检查：STAR 要点、diff、A4 行数估算、事实核对（全部本地确定性代码）
- 版本号管理、快照落库、文件存储与清理
理由：可解释、可测试、零成本、结果稳定。

## 哪些步骤需要大模型判断
- 草稿改写（语言组织、经历整合、要点提炼）
- 打招呼语撰写
- 缺失信息归纳（missing_information）
仅此一次模型调用，且被 JSON 模式 + 编号引用 + 事后本地检查三层约束。

## Agent 如何调用工具
- 当前图节点是直接函数调用（同进程服务），不经过函数调用协议；"工具"即注入的 draft_generator/quality_checker 与本地的分析/检索服务。Chrome 操作、OCR、导出均在 API 层按需调用〔代码确认〕

## 如何限制 Agent 的风险
1. 提示词层：System Prompt 强制"只能用提供的资料、禁止编造、无证据进 missing_information"
2. 结构层：response_format=json_object + 服务端校验（正文非空、evidence 编号必须在本批资料内、非法引用丢弃）
3. 本地检查层：factuality_check 标记新数字/技术名词；STAR 检查；一页估算
4. 人工层：所有结果先为 draft，审核确认才落版本；对外发送（招呼语/简历）每次都要 confirmed=true
5. 数据层：原始简历与旧版本不可变；任务快照留痕

## 如何处理低置信度结果
- 词面无命中时明确标注 fallback/general_context 而非伪装成"检索成功"；无证据引用时自动在 missing_info 追加"模型没有返回有效的个人资料依据，请逐项人工检查"；事实核对输出"需人工核对"清单——低置信内容一律走人工核对路径，不静默通过〔代码确认〕

## 如何进行人工审批
- 双闸门：① 草稿审核（可编辑、看 diff、看证据与缺口 → approve，且超一页硬拒绝 409）② 对外动作审批（BOSS 发送接口的 confirmed 字段 + 发送范围校验：只能发当前岗位的专属简历或该方向当前生效简历）〔代码确认：main.py〕

## 如何记录审计日志
- 无独立审计日志文件（当前项目未发现日志框架）；审计替代物是 agent_runs 表：每次任务的完整输入快照（JD、检索结果、质量检查、图状态）、结果、证据、缺口、错误信息、时间戳全部留痕且不可变（draft 编辑会更新内容但快照同步更新）〔代码确认〕。若需正式审计需补文件/结构化日志〔待定〕

## 如何避免大模型生成危险操作
- 模型只能产出文本（简历/招呼语），不拥有任何工具执行权；对外动作由确定性代码执行且需用户确认；招呼语预填后"尚未发送"，发送是独立的确认接口；不自动投递是产品红线〔代码确认 + 文档确认〕

## 项目中最有代表性的技术难点
1. 防编造链路：提示词约束 + 编号引用校验 + 本地事实核对 + 人工审核的分层设计
2. A4 一页约束：字符宽度估算（东亚宽字符 1.0/其他 0.55，56 行×48 字符）+ 保存闸门 + reportlab 单页渲染兜底
3. 自实现 CDP WebSocket 客户端（无 Selenium/Playwright 依赖），含独立进程管理、登录态隔离、页面结构探测
4. 可解释 RAG：中文 n-gram + 停用词 + 标题加权，并在无命中时诚实降级

## 面试官可能追问的问题及准确回答
- Q: 为什么不用向量检索？ A: 首版目标是可解释与可核对；个人知识库规模小，关键词+权重已够用；无命中时诚实降级为 fallback 并转人工。README 明确"检索效果不足时再评估混合检索"，这是有意识的权衡而非不会。
- Q: 怎么防止模型编造？ A: 四层——提示词硬约束、JSON 结构校验+编号白名单、本地事实核对（新数字/技术名词标记）、人工审核闸门；无证据内容进 missing_information。
- Q: 为什么用 LangGraph 而不是直接写函数？ A: 需要条件路由（一页检查打回/放行）和可替换节点（测试注入假模型与假检查器，test_resume_graph.py 即如此）；同时只保持一张垂直图，不过度设计多 Agent。
- Q: 数据隐私怎么处理？ A: SQLite + 本地文件，密钥只放 .env（gitignore）；调模型前必须显式勾选同意（400 拦截）；只发送检索命中的片段而非整库；OCR 完全本地。
- Q: BOSS 自动化合规吗？ A: 只做用户主动触发的读取（收藏列表/详情页 DOM），不保存密码/Cookie，不绕过验证码，同步结果先预览逐条确认，发送消息/简历每步人工确认，不自动投递。
- Q: 并发怎么办？ A: 个人单机场景 + SQLite 单写者，当前够用；多人化需要换数据库与加锁——明确的下一步项。
- Q: 测试怎么做？ A: 约 139 个测试覆盖解析/检索/JD/LLM 客户端/图/质量/导出/存储/端到端；模型与检查器通过参数注入假实现，不打真实 API。

## 当前方案的优点
- 防编造与可追溯设计完整（证据编号、快照、人工闸门）
- 全链路可解释、可测试、依赖极少（无向量库/浏览器自动化框架）
- 隐私本地化，对外调用最小化且需同意
- 迁移与旧数据兼容有交代（stamp 策略、文件迁移幂等）

## 当前方案的缺点
- 关键词检索的天花板（无语义、n-gram 巧合命中）
- 单用户单机架构（owner_id 硬编码、SQLite、无鉴权）
- 同步阻塞式模型调用（30 秒内），无任务队列
- 前端单文件 App.vue（功能全部集中，维护性一般）
- 无结构化日志/监控/CI
- 对 BOSS 页面结构的脆弱依赖

## 下一阶段最值得做的改进（按性价比排序）
1. 混合检索：Embedding + 向量排序与关键词并存（README 已预留评估口）
2. 模型调用异步化（任务队列/轮询），消除 30 秒阻塞
3. 结构化日志与任务级审计导出
4. 多用户基础：认证 + owner_id 真实化 + PostgreSQL
5. 前端组件拆分与 CI（typecheck+测试门禁）
